## 1. 结论摘要

**没有发现会导致崩溃/死局的可稳定触发缺陷（两端均无 P0）。** 引擎正确性扎实：桌面 `game.js` 与安卓 `GameEngine.kt`、两端求解器
在 8 组核心方法（布雷/3BV/翻开/洪泛/插旗/和弦/胜负判定/求解规则）上逐分支等价，README 的"逐方法移植"成立。

真正值得动手的是三类问题：

| 类别 | 最严重的一条 | 实测证据 |
|---|---|---|
| **性能/开销** | 50×50 开无猜模式，首次点击**同步阻塞主线程约 0.5 秒**，然后**静默降级成普通雷局** | 桌面实测 531ms + 预约耗尽；Node 端 465ms 中位 |
| **UI/UX** | 安卓六个对话框（菜单/统计/键位/自定义/曲线/关于）**完全没有触摸支持**，触摸用户既打不开也关不掉菜单；两端 50×50 格子小到不可读 | GameView.kt:1891-1915 只实现了重开确认框 |
| **产品/健壮性** | 无猜降级无处提示；core API 零输入校验（非法自定义参数会把异常延迟到"第一次点击"才抛） | 两端全仓 grep `noGuessFallback` 仅 core/测试引用 |

另有一处**真机风险**需要尽快在 KPA 上验证：`MainActivity.kt:88-100` 用 `device.isVirtual` 过滤输入事件——若掌机内置手柄上报为
virtual device，手柄会完全失效（游戏的唯一主要输入方式）。

## 2. 实测数据

### 2.1 首次点击耗时（同一引擎，Node / Electron 内测）

| 场景 | 无猜关闭 | 无猜开启 | 无猜降级 |
|---|---|---|---|
| 初级 9×9/10 | 0.1ms | 0.3ms | 0/5 |
| 中级 16×16/40 | 0.2ms | 0.8ms | 0/5 |
| 高级 16×30/99 | 0.2ms | **12.5–15.8ms**（最慢 30.6ms） | 0/5 |
| 自定义 30×30/500 | — | 27.9ms | **3/3** |
| 自定义 50×50/500 | 0.4ms | **465–531ms** | 1–3/3 |
| 自定义 50×50/2125（UI 上限密度） | — | 70.9ms | **3/3** |
| 9×9/68（近满密度） | — | 5.3ms | **2/3** |

结论：`NO_GUESS.maxAttempts=600 / budgetMs=500`（config.js:38-41）在**大棋盘或高密度盘面上必然预算耗尽**。
单次 `solve()` 在 50×50 上 20–44ms，500ms 预算只够 10 余次尝试，命中率远不足以找到可解局 → 用户拿到的是
普通随机雷局且**无任何提示**。安卓走同一算法且 ART 更慢，只会更糟（且无后台线程，全项目无 `Thread/Executor/协程`）。

### 2.2 桌面端渲染与内存（Electron 内测，禁用硬件加速的保守条件）

| 项目 | 实测 |
|---|---|
| 50×50 全量 DOM 重建（2500 节点） | 9.9ms |
| 单格增量更新 ×100 | 0.1ms |
| 同尺寸重开（2500 脏格增量刷新） | 2.6ms |
| 50×50/30 雷首点洪泛（翻开 2463 格 + 渲染） | 6.4ms |
| 页面加载到可交互 | 215ms |
| 进程内存 | Browser 132MB + Tab 137.8MB + GPU 89.2MB + Utility 43.5MB ≈ **402MB** |

桌面渲染路径（`ui.js` 的 dirty 增量更新）表现良好，无需优化。内存与体积是 Electron 固有成本（见 2.3）。

### 2.3 体积开销

| 产物 | 体积 |
|---|---|
| 桌面 macOS dmg | 98.2MB |
| 桌面 Linux AppImage | 108.4MB |
| 桌面 Windows portable exe | 74.2MB |
| 安卓 release APK（R8 后） | **178KB** |
| 安卓 debug APK | 2.16MB |

同一个游戏，桌面端比安卓端重 **550 倍**。这是 Electron 的必然代价，但项目没有做任何减重：
`package.json` 的 `files` 已正确收窄（只含 main/preload/icon/src），进一步的选项只有换 Tauri/自绘窗口（成本高，
不建议为此项目做）。**结论：桌面体积属可接受成本，不作为问题项。**

## 3. 优先处理清单（P1）

按"修起来的性价比"排序。

### P1-1 无猜模式阻塞主线程 0.5s + 静默降级（两端）

- 证据：`src/game.js:169-182` / `GameEngine.kt:197-209`；预算只在每次完整求解**之后**检查；调用链全在 UI 线程
  （`app.js:531-537` → `ui.js:249`；`GameView.kt:498` → `GameEngine.kt:277-279`）。
- 影响：50×50 开无猜 = 点一下卡半秒，且拿到的仍是必猜局；`noGuessFallback` 两端 UI 均未消费（README 却宣称"不会放出必猜局"）。
- 建议（三条独立、可分别做）：
  1. 把生成放到工作线程 / Web Worker（桌面 `worker_threads` 或渲染进程 Worker），期间显示"生成中"；
  2. 预算降到 ~1 帧（16ms）并只在低密度（≤20%）棋盘启用重生成，超预算直接声明"本局无解保护不可用"；
  3. 无论如何把 `noGuessFallback` 接到 UI（HUD 角标或开局面板），兑现"保守判定"的诚实承诺。

### P1-2 安卓：每次操作整盘重绘静态层，引擎现成的 `dirty` 被丢弃

- 证据：`GameView.kt:458-461` 无条件 `invalidateBoardCache()` → `1199-1206` 全盘 `drawCell`；
  而 `engine.dirty` 只在 `markRevealAnimFromDirty()`（478-485）消费一次即清空。
- 对照：桌面版走 `ui.js:115-124` 的 dirty 增量（实测单格更新 0.1ms、2500 格 2.6ms）。
- 影响：50×50 每次点击/插旗要 CPU 光栅化 2500 格（约 1.2–3 万次 Skia 调用）；叠加 `drawCellContent` 每格
  `textPaint.reset()`（1349-1354）、`drawEmoji` 每 emoji `emojiPaint.reset()`（1364-1367），快速连点明显掉帧。
- 建议：静态层只重绘脏格并集（`clipRect` + 只画脏格），`resetRound`/终局才全量重建；顺带把 Paint 改成预配置复用。

### P1-3 安卓：首点洪泛时"整盘重建 + 上千动态格动画"同帧

- 证据：`GameView.kt:478-485`（dirty 中每个新翻开格进 `revealedAnim`）+ `1215-1234`（每帧 `HashSet` + `sorted()`）+ `1124-1128`（逐格 `save/scale/restore`）。
- 影响：低雷密度大棋盘首点最坏帧可达数十毫秒。
- 建议：动画格数截断（如仅视口内 / 上限 256 格，其余直接跳终态）。

### P1-4 安卓：六个覆盖层零触摸支持

- 证据：`onTouchEvent`（1889-2041）只处理 `Overlay.ConfirmNewGame`；其余覆盖层下 `cellAt()` 直接 `return null`（2044-2053）
  且 `faceHit` 被 `overlay == None` 屏蔽（1936-1940）→ `return false`。
- 影响：纯触摸设备上，主题/静音/无猜/统计/键位/自定义/曲线全部不可达，菜单打开后也关不掉（只能靠系统返回手势）。
- 建议：抽一个"覆盖层行命中"共用函数（与绘制同一套矩形），`ACTION_UP` 派发到与手柄一致的 `activate*` 路径；
  底栏或 HUD 加一个可点的"菜单"入口。

### P1-5 两端：50×50 棋盘不可读（格子 ≈15–16px，字形 7.5–8px）

- 证据：桌面 `config.js:46-49` + `app.js:62-69` → 50×50 时 `min(1150/50, 760/50)=15px`，字号 `cell*0.5=7.5px`；
  安卓 `GameView.kt:102 MIN_CELL=16f` + `1283/1345` 的 `cell*0.5`，未翻开格斜面固定 `2f`（1277-1280）再吃掉约 1/4 面积。
- 影响：项目主打的"最大 50×50"实际不可玩。
- 建议：桌面加 `--cell-size` 缩放（Ctrl +/-）或把 cell 下限提到 22px 并允许棋盘区滚动（`#app` 已是 `overflow:auto`，
  把 `boardMaxH` 上限放开即可）；安卓 `MIN_CELL` 提到 22–24f、字号 ≥`cell*0.62`、斜面随格子缩放，或超大棋盘隐藏斜面只留描边。

### P1-6 安卓真机风险：`device.isVirtual` 一刀切过滤输入

- 证据：`MainActivity.kt:88-100`。
- 影响：若 KPA 内置手柄/按键上报为 virtual device，**整个游戏无输入可用**（View 不可聚焦，super 也不会处理）。
- 建议：改按 `source & SOURCE_GAMEPAD/JOYSTICK` 或键码白名单判定；至少加"从未收到手柄键则不过滤"的兜底。
  这是本次审查中唯一"命中即不可玩"的风险，建议尽快上真机验证。

### P1-7 无猜降级无提示（两端）

见 P1-1 第 3 条。单独列出是因为它是**产品诚信**问题：README 承诺"不会放出必猜局"，而实测 50×50 必然降级。

### 4.2 引擎侧分配（两端共同，安卓更重）

- 安卓 `GameEngine.kt:67` `dirty` 用 `Pair<Int,Int>`：50×50 一次 `markAllDirty()` = 2500 个 Paired + 5000 个装箱 Integer；
  `floodFill`（294）用 `ArrayDeque<Pair>`。**而 `GameView.kt:161-163` 的注释明确写了要避免 Pair 装箱——app 做到了，core 没有。**
- 桌面 `game.js:39-49` `dirty` 用 `"r,c"` 字符串键：每次 `markDirty` 分配一个字符串（2500 格 = 2500 个串）。首点洪泛实测 6.4ms 仍可接受，
  属可优化项而非问题。
- 建议（安卓）：`dirty` 换 `Long` 键（`row shl 32 or col`）或位图 + 计数；`floodFill` 用 `ArrayDeque<Int>`。

### 6.2 设计选择（不是 bug，但建议在 KDoc/README 写明）

## 8. 值得保留的做法（审查中确认做对了的部分）

- **桌面渲染**：dirty 驱动的增量 DOM 更新（实测单格 0.1ms、2500 格 2.6ms）+ 事件委托（容器级 3 个监听器而不是每格 3 个）+ `renderAll` 仅在尺寸变化时重建。
- **Electron 安全基线**：`sandbox:true` + `contextIsolation:true` + `nodeIntegration:false` + CSP（无 `unsafe-inline`）+ `will-navigate`/`setWindowOpenHandler` 双拦截。
- **计时**：`Date.now()` 锚点 + 250ms 刷新，彻底消除 `setInterval` 漂移（`app.js:18-52`）。
- **算法**：迭代式洪泛（显式栈，无递归深度风险）、Fisher-Yates 布雷、两端一致的求解器三规则 + 全局规则 + 终局全盘校验。
- **安卓绘制**：Pain/Path/RectF 复用、`metrics()` 缓存、位图静态层 + 动态格分层、命中与绘制共用矩形的约定在**棋盘格/难度按钮/确认框**三处确实落实了（用 `metrics()`/`diffBtnRects()`/`confirmButtonRects()` 共用函数）。
- **安卓 3BV/无猜**：与桌面逐句对齐，且 `compute3BV` 的"0 区域计 1 + 未被覆盖数字格各计 1"语义正确。
- **统计口径**：`ready→任意状态`才计一局，覆盖"一次操作直接 ready→won"的胜率口径洞（`ui.js:79-83`）。

## 11. 性能与 UX 改造记录（2026-10-12 同日，第二批已完成）

§9 第二批全部条目已实现并验证。测试总数：桌面 **76 项**、安卓 core **69 项**，全绿；`:app:assembleDebug` 通过；打包（`electron-builder --dir`）后 worker 实测可用。

### 无猜生成不再阻塞 UI（P1-1，两端）

- **架构**：雷位生成抽成不持有棋盘状态的纯函数——桌面 `src/generator.js`（UMD，渲染进程/Node/主进程共用）与安卓 `GameEngine.planMines`（companion，可跨线程调用）；引擎只保留 `applyPlan`/`applyPlanAndReveal` 在 UI 线程落地。
- **桌面**：主进程通过 `worker_threads` 执行生成（`src/generator-worker.js`），打包配置新增 `asarUnpack` 并为 worker 做 `app.asar → app.asar.unpacked` 路径替换（worker_threads 不走 asar 补丁）。渲染进程 await 期间显示「正在生成无猜雷局…」，新游戏/切难度以 `generationSeq` 作废过期结果；worker 失败自动回退同步路径。
- **安卓**：`GameView.startAsyncFirstReveal` 用后台 `Thread` 调用 `planMines`，结果 `post` 回 UI 线程应用；生成期间 `canAct()` 为假（忽略棋盘操作），HUD 显示同款提示。
- **预算策略**：预算 500ms → 800ms（异步下等待不再冻结界面），并新增「按单次耗时预估、预算内总量不足 `MIN_EXPECTED_ATTEMPTS = 20` 时立即降级」——避免 50×50/2125 这类注定失败的配置白等。
- **实测**：50×50/500 首点从**冻结 531ms → 41ms 返回**（后台继续到预算），主进程 IPC 延迟 0.5ms；高级局无猜仍在 10–40ms 内生成可解局（20/20 成功）；50×50/500 在 800ms 预算下恢复约 1/3–1/2 的无猜成功率。

### 安卓渲染（P1-2 / P1-3 / P2 系列）

- 静态层位图接入引擎 `dirty`：一次操作**只重绘变化格**（格子不透明不重叠，直接覆盖绘制），仅在尺寸/主题/新局时整层重建；旧位图不显式 `recycle`（避免硬件纹理仍在使用时崩溃）。
- 数字/emoji 改用预配置画笔（去掉每格 `Paint.reset()`）；底栏按钮标签宽度缓存（去掉每帧 4 次 `measureText`）；`boardViewport()` 复用 RectF。
- 光标移动只失效新旧两格（长按方向键 25Hz 不再整屏重绘）；计时秒跳只失效 HUD 区域。
- 单次翻开超过 256 格时跳过逐格缩放动画（大洪泛最坏帧）。

### 两端 50×50 可读性（P1-5）
